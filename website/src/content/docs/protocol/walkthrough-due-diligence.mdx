---
title: "Walkthrough: Cross-Exchange Due Diligence"
description: "Broker decomposes entity-based intent into 6 exchange queries with heterogeneous pricing, mixed mutability, and deal-level budget tracking."
---

> An AI agent needs a due diligence package on a company. The Broker decomposes that intent into 6 resource types across 4+ Exchanges, aggregates heterogeneous pricing, tracks costs against a deal-level budget, and delivers mixed-format results — all through the same RAMP v1.0 protocol.

## The Scenario

| | Details |
|---|---|
| **Agent** | `dd-analyst` at `lawfirm.com` |
| **Broker** | `broker.lawfirm.com` |
| **Target** | Acme Corp (D-U-N-S 123456789) |
| **Budget** | $1,500 per deal (`deal:acme-acquisition`) |
| **Resource types** | Credit report, court filings, property records, SEC filings, news articles, patents |
| **Exchanges** | 4+ (Credit, Legal, Property, SEC/free) |

The agent does not know individual document URIs — it knows a company name and an identifier. The Broker is the intelligence layer that decomposes this entity-based intent into specific resource queries across domain-specific Exchanges.

### The Six Resource Types

| # | Resource | Exchange | Pricing Model | Mutability | Est. Cost |
|---|----------|-------------|---------------|------------|-----------|
| 1 | D&B credit report | `exchange.creditdata.com` | PER_RECORD ($61.99) | DYNAMIC | $61.99 |
| 2 | PACER court filings (3 found) | `exchange.legaldata.com` | PER_PAGE ($0.10/page, ~105 pages) | STATIC | $10.50 |
| 3 | CoreLogic property records (5 properties) | `exchange.propertydata.com` | PER_RECORD ($2.50/record) | STATIC | $12.50 |
| 4 | EDGAR SEC filings (4 10-K/10-Q) | `exchange.secdata.com` | FREE | STATIC | $0.00 |
| 5 | News articles (8 recent) | `exchange.newsagg.com` | PER_ACCESS ($0.05/article) | STATIC | $0.40 |
| 6 | Patents citing Acme tech (2 patents) | `exchange.secdata.com` | FREE | STATIC | $0.00 |

**Total estimated: $85.39 out of $1,500 budget**

## Step 1 — Agent Request (RAMPRequest)

The agent sends a single high-level request to its Broker. The key field is `budget_scope` — it ties all costs across every Exchange to a single deal identifier:

```json
POST https://broker.lawfirm.com/ramp/v1

{
  "ver": "1.0",
  "id": "ramp-dd-001",
  "requester": {
    "id": "dd-analyst",
    "domain": "lawfirm.com",
    "type": "REQUESTER_TYPE_AGENT",
    "uris": [],
    "intended_use": ["FUNCTION_AI_INPUT"],
    "scopes": ["credit:read", "legal:read", "property:read", "sec:read", "news:read"],
    "signature": "ed25519:f1a2b3c4d5e6...",
    "signature_algorithm": "ed25519"
  },
  "constraints": {
    "budget_scope": "deal:acme-acquisition",
    "period_budget": {
      "amount": 1500.00,
      "currency": "USD"
    },
    "max_data_age": "604800s",
    "reporting_capable": true
  },
  "ext": {
    "entity_name": "Acme Corp",
    "entity_duns": "123456789",
    "dd_resource_types": [
      "credit_report",
      "court_filings",
      "property_records",
      "sec_filings",
      "news_articles",
      "patents"
    ]
  }
}
```

**Key design point**: The `uris` field is empty. The agent knows a company, not document URIs. The Broker's job is to decompose this entity-based intent into specific resource queries. This is the two-phase model: **discover** (Broker's domain-specific logic) then **access** (RAMP protocol).

The `ext` field carries domain-specific metadata (entity identifiers, requested resource types). The core protocol doesn't need to understand these — the Broker does.

---

## Step 2 — Broker Decomposition

The Broker is the intelligence layer. It takes the entity-based intent and decomposes it into 6 exchange-specific queries. This decomposition logic is Broker-internal — the protocol does not prescribe it.

```
Input:  "Due diligence on Acme Corp (DUNS: 123456789)"

Broker decomposition:
├── Credit Exchange     → D&B report for DUNS 123456789
├── Legal Exchange      → PACER search: party="Acme Corp" + CIK from SEC
├── Property Exchange   → CoreLogic: owner="Acme Corp" + known addresses
├── SEC Exchange        → EDGAR: CIK 0001234567 (resolved from DUNS)
├── News Exchange       → Entity search: "Acme Corp" last 90 days
└── SEC Exchange (reuse)→ USPTO: assignee="Acme Corp"
```

The Broker resolves entity identifiers using domain-specific APIs (SEC EDGAR full-text search for CIK, D&B API for DUNS lookup, etc.) **before** making RAMP queries. Once it has specific resource URIs, it fans out `ResourceQuery` requests to each Exchange.

The Broker collects all 6 `ResourceResponse` results and builds an aggregate cost picture before committing any transactions. This is the critical intelligence layer — the agent sees a unified view across heterogeneous Exchanges.

**Budget check passes**: $85.39 < $1,500.00 available. The Broker proceeds to execute transactions.

**What the Broker verified before proceeding:**
1. **Freshness**: Credit report `data_as_of` (today 06:00) is within `max_data_age` (7 days)
2. **Restrictions**: All offers permit `FUNCTION_AI_INPUT`
3. **Budget**: Total estimated cost ($85.39) is within the deal budget ($1,500)
4. **Dedup**: No duplicate resources across Exchanges (each URI is unique)
5. **Mutability**: Tagged each resource — agent will verify SHA-256 on STATIC resources, skip hash check on DYNAMIC (credit report)

## Step 7 — Mixed Delivery

The Broker fetches all resources in parallel. Each resource type has a different delivery format:

| Resource | Delivery | Format | Hash Verification |
|----------|----------|--------|-------------------|
| D&B Credit Report | JSON API (signed URL) | Structured JSON | Skipped (DYNAMIC) |
| PACER Court Filings | Signed URL to CDN | PDF | SHA-256 verified (STATIC) |
| Property Records | JSON API (signed URL) | Structured JSON | SHA-256 verified (STATIC) |
| SEC EDGAR Filings | Signed URL to CDN | HTML | SHA-256 verified (STATIC) |
| News Articles | Signed URL to CDN | HTML | SHA-256 verified (STATIC) |
| Patents | Signed URL to CDN | HTML | SHA-256 verified (STATIC) |

**Hash verification by mutability:**
- **STATIC resources** (filings, records, articles, patents): The Broker computes SHA-256 of the delivered bytes and compares against `identity.content_hash` from the Offer. Mismatch is auto-disputable.
- **DYNAMIC resources** (credit report): No hash verification. The content reflects the latest data. `data_as_of` confirmed freshness at offer time.

## What This Walkthrough Demonstrates

### 1. Broker as Intelligence Layer

The agent sends one high-level request. The Broker handles:
- **Entity resolution**: DUNS to CIK, company name to PACER cases, company name to property addresses
- **Exchange routing**: 6 queries to 4+ Exchanges, each with domain-specific URIs
- **Cost aggregation**: Heterogeneous pricing models normalized into a single budget view
- **Freshness validation**: `max_data_age` checked against `data_as_of` for DYNAMIC resources
- **Dedup**: `ResourceIdentity` prevents paying for the same resource twice across Exchanges

### 2. Six Pricing Models in One Workflow

| Model | Resource | How It Works |
|-------|----------|-------------|
| `PER_RECORD` | Credit report | $61.99 per report — high-value, dynamic data |
| `PER_PAGE` | Court filings | $0.10 per page — granular, document-level metering |
| `PER_RECORD` | Property records | $2.50 per record — structured data access |
| `FREE` | SEC filings | $0.00 — public government data, metered for reporting |
| `PER_ACCESS` | News articles | $0.05 per article — low-value, high-volume |
| `FREE` | Patents | $0.00 — public data, usage tracked but not billed |

All pricing models use the same `Pricing` message. The `unit_cost` field enables cross-exchange comparison regardless of the underlying model.

### 3. Mixed Mutability

- **DYNAMIC** (credit report): No `content_hash`. Content reflects latest data. `data_as_of` signals freshness. Hash mismatch is expected, not disputable.
- **STATIC** (everything else): `content_hash` with SHA-256. Agent verifies integrity on delivery. Mismatch is grounds for `DisputeTransaction`.

The same `ResourceIdentity` message handles both — the `resource_mutability` field drives verification behavior.

### 4. Cross-Exchange Budget Tracking

The `budget_scope: "deal:acme-acquisition"` field in `RequestConstraints` enables deal-level spend tracking across all Exchanges. The Broker:
1. Checks cumulative spend before each transaction batch
2. Denies transactions that would exceed the budget
3. Reports actual spend per Exchange in `UsageReport.ext.budget_scope`
4. Maintains a ledger for audit (which Exchange got how much for what)

### 5. ROI: Licensed Data vs. Manual Research

| | Licensed (RAMP) | Manual (Paralegal) |
|---|---|---|
| **Time** | ~30 seconds (parallel fetch) | 2-4 days |
| **Cost** | $85.39 (data) + Broker fee | $6,000-$12,000 (labor) |
| **Completeness** | 6 resource types, automated | Risk of missed sources |
| **Audit trail** | Transaction IDs, billing IDs, report IDs per resource | Paralegal timesheets |
| **Reproducibility** | Same query produces same results | Varies by researcher |

RAMP replaces the **data acquisition** layer of due diligence, not the analysis. The agent still reasons over the data — but it acquires it in seconds instead of days, with full provenance and audit trail.

## Protocol Summary

| Step | RPC | What Happens |
|------|-----|-------------|
| 1 | — | Agent sends entity-based intent to Broker |
| 2 | — | Broker decomposes into 6 domain-specific queries |
| 3 | `DiscoverResources` (x6) | 6 parallel SupplyQueries to 4+ Exchanges |
| 4 | — | Broker aggregates offers, checks budget |
| 5 | `ExecuteTransaction` (x4) | Batch transactions to each Exchange |
| 6 | — | Mixed-format fetch (JSON, PDF, HTML) with hash verification |
| 7 | `ReportUsage` (x6+) | Per-transaction usage reports, all linked via budget_scope |

**Authentication at every step:**
- **Agent to Broker**: `Requester.signature` (Ed25519)
- **Broker to Exchange**: `IntermediaryHop.signature` + forwarded `Requester.signature`
- **Exchange to Agent**: `exchange_signature` on every Offer (Ed25519, stateless verification)
- **Signed URLs**: HMAC-SHA256 (Exchange-CDN shared secret, agent identity bound)
